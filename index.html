Nexy, a RAG assistant that keeps itself up to date

The chatbot on NextAct Solutions' website answers visitors from the company's own pages, cites its sources and captures leads. I built it, then built the pipeline that refreshes its knowledge after every deployment, and spent most of my time on the bugs that only show up in production.

How it works

Two paths share one vector store. A visitor's question goes through an agent that decides whether to search the knowledge base or save a lead. A push to main deploys the site, then refreshes that knowledge base from the live pages.

flowchart LR
  V[Visitor] --> W[React chat widget]
  W -->|/chatbot via nginx| API[FastAPI]
  API --> A[LangChain agent
Gemini + middleware]
  A -->|search tool| C[(ChromaDB)]
  A -->|lead tool| L[(SQLite + back-office API)]
  P[Push to main] --> CI[CI tests]
  CI --> D[Deploy over SSH]
  D --> S[deploy-vps.sh]
  S -->|front content changed| K[sync_knowledge.py]
  K -->|sitemap + Firecrawl| R[Clean, hash, compare]
  R -->|changed pages only| C
  R -->|restart chatbot| API

What I built

  • An agent, not a fixed pipeline.LangChain create_agent with two tools: knowledge search and lead capture. Middleware handles retries on Gemini 503s only, a cap on model calls per turn, and tool errors.
  • Incremental knowledge sync.Reads the page list from the sitemap, scrapes each page fresh, hashes the cleaned text and re-embeds only pages whose hash changed. Pages gone from the sitemap are removed.
  • CI/CD integration that never blocks a release.The deploy script runs the sync only when front-end content changed, and maps the sync's exit codes (0 to 4) to a restart, a GitHub warning, or nothing.
  • Safeguards for unattended runs.Rejects error pages, near-empty renders and pages that lost half their content. Aborts without writing if over 30% of pages fail or over 30% would be deleted.
  • Manual and scheduled runs.sync-nexy and sync-nexy-force from the GitHub Actions tab, plus a weekly run for content edited in the admin.

Debugging log

The problems that taught me the most. Each one passed every unit test and only appeared with real data or a real browser.

Nexy quoted figures that were never on the site

front-end × scraper
Symptom
The index held lines like +-373 Projets livrés and -900,3% Disponibilité visée. Three pages were also re-embedded on every sync although nothing had changed.
Cause
Animated counters computed their progress from the animation-frame timestamp. In the scraper's headless browser that clock lagged behind performance.now(), so progress went negative and the counter froze on a wrong value that changed between runs.
Fix
One shared useCountUp hook: it starts from the real value, measures time with a single clock and always ends on the real value through a timer.
Proof
In a browser with frames blocked, the pages show +30, 99,9% and < 1 h, with no negative values.

Edited pages looked unchanged

caching
Symptom
Two syncs in a row reported every page as unchanged, which looked like success.
Cause
Firecrawl returns a cached copy up to two days old by default (maxAge). A page edited by a deployment could be read from that cache and keep its old version in Nexy, with no warning.
Fix
max_age=0 on every scrape, then a check that fresh scrapes of the same page hash identically, so the sync doesn't re-embed for nothing.

A visitor saw "Model call limits exceeded"

agent behaviour
Symptom
On a question about training courses, the reply was the middleware's internal message: Model call limits exceeded: run limit (5/5).
Cause
The limit middleware ends the run with its own message. Removing the tools on the last call didn't help: with function calls in the history, Gemini still asked for a tool, whether given tools=[] or tool_choice="none".
Fix
On the last allowed call, the turn is rewritten as a plain question that carries the documents already retrieved. Gemini then answers from them.
Proof
With the limit lowered to 2, the real model returns a proper answer instead of the fallback message.

The chatbot kept answering from old data after a sync

vector store
Cause
Chroma keeps its search index in memory. A second process can write new chunks: the record count updates, but searches in the running API still return old results, including deleted chunks. I reproduced it with 5 and 3,000 chunks, and a fresh client in the same process was still stale.
Fix
The deploy script restarts the chatbot only when the sync reports changes, which costs a few seconds of chatbot downtime and none for the site.

A regex that could hang the sync

text cleaning
Cause
A pattern meant to strip a calendar's digits backtracked exponentially when a letter followed a long digit run. The marketing page contains a 58-digit run, protected only by a line break.
Evidence
32 digits + letter    0.5 s
40 digits + letter   24.8 s
58 digits + letter   > 30 s (stopped)
Fix
\b\d{16,}\b, which matches the same runs in linear time. The same pass fixed broken links, escaped characters and false headings.

Streaming, measured before shipping

latency
Experiment
I added Server-Sent Events end to end, with status events ("searching…"), tokens and a final cleaned message.
Result
The first word arrived at 6.9 s and the full answer at 7.7 s. Streaming saved under 2 seconds, because the time goes into searching and model reasoning before the first word.
Decision
Kept on its own branch. Reducing search loops and reasoning time is the change that would actually help.

What a sync reports

The deploy script reads the sync's exit code. A sync problem never fails the deployment: it surfaces as a warning in the GitHub Actions run.

CodeMeaningDeploy script reaction
0Already up to dateNothing
1Aborted, nothing writtenWarning
2Nothing changed, some pages failedWarning
3Knowledge base updatedRestart the chatbot
4Updated, some pages failedRestart

Known limits and next steps

  • Admin edits wait for the weekly run.A webhook from the PHP back-office, targeting only the pages that show the edited content, would make updates near-immediate.
  • Model quota.A free-tier key allows about 20 model calls a day, and one question often takes two or more. Production needs a paid key and per-visitor rate limiting.
  • Latency.Most of the 7 to 10 seconds is search loops and model reasoning. That is where the next gains are.
  • Single process.The in-memory index ties the API to one worker. Moving to a Chroma server would remove the restart and allow scaling.
